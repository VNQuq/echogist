# Design: Bulk mode — a whole folder through the EchoGist core

Generated by /office-hours on 2026-09-04
Branch: main
Repo: echogist (local, personal-use)
Status: APPROVED
Mode: Builder

## Problem Statement

EchoGist processes one file at a time. Menu #2 ("batch") multi-selects videos and produces
MP3 only, offline and free; everything past extraction stays single-file. The operator has a
lecture library on disk and wants to point the tool at a folder, walk it recursively, and put
every media file through the full core: MP3, transcript, summary.

Two things make that more than a loop. The paid stage costs real money per file, so a folder
of forty lectures is a ~$21 keystroke that today has no aggregate gate in front of it. And
recursion introduces duplicate filename stems, which turns latent naming assumptions into
corruption of paid output once any concurrency exists.

## What Makes This Cool

The pre-scan. Point at a folder, get a table: per-folder file counts, total hours, total bytes,
how many already have a transcript on disk, a projected dollar figure, and a list of duplicate
stems. Nothing runs, nothing is spent, nothing is written except a cache file. You see your
library and decide from evidence instead of from a filename list.

## Constraints

- **Killswitch (CLAUDE.md).** SUMMARIZE is the only network stage. Everything left of it,
  including token estimation, is local and offline. The pipeline must run end to end in CI
  against a stub summarizer.
- **Artifact-based recovery, not a job engine.** Durable state is the saved artifacts under
  `output/{audio,transcripts,summaries}`. No `job.json`, no history layer.
- **Fail loud, return to menu.** Never a crash, never a silent truncation or skip.
- **Config is data, not code.**
- **One GPU.** Whisper cannot be parallelised across files (CUDA errors, OOM: openai/whisper
  #1771, SYSTRAN/faster-whisper #1333). ffmpeg extraction parallelises fine.
- **No ffprobe.** `imageio-ffmpeg` ships ffmpeg only; duration and bitrate come from parsing
  `ffmpeg -i` stderr (`extract._probe_duration` already does the duration half).
- Windows-only at runtime, developed in WSL2. `output/` is machine-local and gitignored.

## Premises

1. Bulk runs the full pipeline per file, not just transcripts. (Operator-confirmed.)
2. Transcription sequential, extraction parallel. (Confirmed by prior art.)
3. A rough duration-derived gate at scan, one exact token-derived gate immediately before
   any paid call. Revised during the session: the exact gate is the ONLY global barrier;
   extract and transcribe stream per file. (dec-7f2697f7)
4. mp3 re-encode trigger is size > 222 MiB OR audio bitrate >= 320 kbps, with an
   anti-inflation guard that never re-encodes a file already at or below the ~190 kbps
   encoder target. (dec-c3adfe5b) **This premise governs a SEPARATE doc, not this one.**
5. The scan needs one `ffmpeg -i` per file, cached by (path, size, mtime_ns).

### Premise 4 was revised during the session

Size is bitrate multiplied by duration, so a size-only rule cannot tell a high-bitrate file
from a merely long one: past 2.5 hours the 222 MiB line starts catching 128 kbps lectures and
re-encoding them UP to ~190 kbps, larger and twice-lossy. Full reasoning and the resolution
live in the separate 1b doc and in `dec-c3adfe5b`.

## The naming problem (dec-b3a3181c)

Verified in code, line by line. **Severity differs per site, and the difference decides the
build order.**

**Already broken today, sequentially:**

- The resume file is keyed on the bare source stem, no date, no dedup
  (`menu.py:308-309`: `naming.summary_stem(source_stem)`), and `menu._load_resume:187`
  accepts any partial where `0 < len(partial.synthesis) <= k` with no check of which
  transcript produced it. `_clear_resume` deletes the partial on success, so this needs file
  A to have died mid-summary; then a later file B with the same stem resumes A's phases and
  B's paid summary carries A's prose and A's timecodes. The anchor validator passes it,
  because the timecodes are real, just from the wrong recording. Narrow, but live, and silent.

**Sequential-safe, parallel-unsafe (only bites under a summarize pool):**

- `transcribe.save_transcript:153` calls `naming.dated_artifact_path` with no `taken` set.
- `summarize.save_raw_result:311` calls `naming.dedup_path` with no `taken` set.

Both select-then-write immediately, so a sequential run is fine. Two concurrent workers select
the same free name in the gap before either writes, and one artifact silently overwrites the
other. That is exactly the race `batch._plan_output_paths` (`batch.py:296-323`) devotes three
docstring paragraphs to for mp3 names, reopened one directory over.

**The four fixes, in build order:**

1. Key the resume file on a short hash of the resolved source path instead of the stem.
   (Fixes the live bug. Cheap, independent of everything else.)
2. Add a `taken` parameter to `transcribe.save_transcript`.
3. Add a `taken` parameter to `summarize.save_raw_result`.
4. Plan mp3 + transcript + resume paths for the whole run up front, single-threaded, in
   memory, sharing one `taken` set (extending `batch._plan_output_paths`).

**Summaries cannot join step 4.** The summary filename comes from the LLM-generated title,
which does not exist until after the paid call returns. The `_plan_output_paths` pattern does
not transfer. Instead the run holds a `claimed: set[Path]` that is passed into
`save_raw_result` at call time and updated as each summary lands.

## Approaches Considered

### Approach A: Scan first (CHOSEN)
`scan.py` ships alone as a read-only menu item. Recursive walk, cached probe, per-folder
tables, rough cost projection, stem-collision report. No `bulk.py`, no paid path.
Effort S-M: one new module, one `extract` signature widening, one menu row, six test groups.
Risk low, and fully reversible (delete the module and the menu row).

### Approach B: Full bulk v3 in one change
Scan plus streamed extract/transcribe, exact gate, summarize pool, and all four naming fixes.
Effort L, risk medium, roughly 900 lines including tests. Deferred to increment 2.

### Approach C: Wavefront via Message Batches API
As B, but summaries are submitted as batches keyed by phase index. Halves the bill and removes
the thread pool entirely. Rejected for now: asynchronous delivery breaks "summaries tonight",
and the `fallbacks` parameter is not accepted on the Batches API, so a model refusal drops a
document with no safety net. Revisit if the real folder turns out to be large.

## Recommended Approach

A, then B. This is sequencing, not a scope cut. The scanner is the part the operator described
sensorially, it is offline and free, and its output
on the real folder is the input for every remaining decision: whether the pool is worth
building, and how real the stem-collision problem is in this particular tree.

## Increment 0: the resume key (do this first, it is live)

Independent of the scanner and of bulk. It is in this doc because the recursion is what makes
it matter, but it ships alone and first.

**A signature change is required first.** `_run_summary(deps, settings, model_config,
transcript_text, source_stem)` (`menu.py:219-224`) receives only a string; the Path lives at
the two call sites, `menu.py:521` (`source.stem`) and `menu.py:730` (`chosen.stem`). Add
`source_path: Path`, update both call sites, and keep `source_stem` for the fallback title.

Key the resume file on:

```python
hashlib.blake2s(str(source_path.resolve()).casefold().encode(), digest_size=8).hexdigest()
```

`casefold()` because `Path.resolve()` does not reliably normalize case on Windows, and the
same file picked twice with different casing would otherwise produce two keys and silently
lose the resume.

The two entry points differ on purpose: the local-file flow's source is the media file, the
saved-transcript flow's source is the `.txt`. Those are different identities and must not
collide, so the hash is taken over whichever path that flow actually opened.

Existing `.resume/*.json` files are keyed the old way and become unreachable. They are
within-run partials, not durable artifacts. Sweep them by shape, not by date: delete any
`.resume/*.json` whose stem does not match `^[0-9a-f]{16}$`, and say so in one line.

**Success criterion:** two source files with the same stem, the first killed mid-summary, the
second run to completion, and the second summary contains none of the first's phase prose.

## Increment 1: the scanner (this doc's deliverable)

### Data model (eng review, issue 1)

Two types, not four. `MediaProbe` and a separate per-file record are the same thing by
lifecycle, and per-folder statistics are a grouping, not an entity:

```python
@dataclass(frozen=True)
class MediaFile:
    path: Path
    rel: Path
    size: int
    duration: float | None
    audio_kbps: float | None
    has_video: bool


@dataclass(frozen=True)
class ScanResult:
    files: tuple[MediaFile, ...]
    unreadable: tuple[tuple[Path, str], ...]  # path, reason
    placeholders: tuple[Path, ...]
```

Folder rows are `group_by_folder(result)`, a function, used once at render time.

### Pipeline

```
  pick_dir
     |
     v
  scan.walk(root, recursive=True) ------> unreadable[] , placeholders[]
     |  prune output/ and seen-junctions in dirnames[:]
     |  filter batch.CONVERTIBLE_SUFFIXES
     v
  for each path:  cache hit? --yes--> MediaFile
     |                 |no
     |                 v
     |            extract.probe_media(path, exe, runner)   [timeout -> unreadable]
     |                 |
     |                 v
     |            cache[key] = {duration, audio_kbps, has_video}
     v
  ScanResult
     |
     +--> group_by_folder ------> ui.table rows (ui.human_size for bytes)
     +--> transcript_index -----> "N candidate transcripts" per row
     +--> collision groups -----> duplicate-stem report
     +--> project_cost ---------> totals block, upper bound, tier-labelled
     |
     v
  cache flush (.part -> os.replace)   <- also on Ctrl-C
```

### Walk

- **One walker for the whole project (eng review, issue 4).** `scan.walk(root, *, recursive)`
  is the single implementation; `batch.expand_selection` is rewritten to delegate with
  `recursive=False`. The suffix filter, the resolved-path dedup and the junction guard then
  exist once. `test_batch.py:53` (`..._expands_a_directory_without_recursion`) and its four
  siblings become the regression harness that proves the batch flow is unchanged.
- `os.walk` with symlinks not followed (the default), reusing `batch.CONVERTIBLE_SUFFIXES`
  verbatim. Do not fork the list.
- **Track visited directories by `Path.resolve()` in a `seen` set** (same shape as
  `batch.expand_selection`'s dedup at `batch.py:290`). `followlinks=False` does not protect
  against NTFS directory junctions, which cloud-sync clients create routinely in a media
  library, and a junction loop would walk forever. Both this and the `output/` skip are applied
  by pruning `dirnames[:]` in place during the walk, not by filtering afterwards.
- `output/transcripts` and `output/.scan-cache.json` are always `deps.base`-relative, wherever
  the scan root happens to be. The skip rule below is about the scanned tree, not about them.
- **Skip any directory named `output/` under the scan root.** EchoGist's own artifacts must
  never be counted as sources, or increment 2 would re-process its own output.
- **Unreadable is defined by the probe, not by the exit code.** `ffmpeg -i` always exits
  non-zero by design (`extract._probe_duration` documents this: "At least one output file must
  be specified"), so exit status carries no signal. A file is unreadable when `stat` raises
  `OSError`, or when its probe stderr contains no `Duration:` line. Unreadable files are listed
  in their own row with their paths, never dropped silently, and never counted in the totals.

### Probe

**Resolve the ffmpeg binary once, before the walk.** `extract._default_ffmpeg_exe` raises
`ExtractError` when imageio-ffmpeg is missing or corrupt; under the unreadable rule below a
missing binary would otherwise mark all 500 files unreadable instead of failing loud once.

**Skip cloud placeholder files.** A lecture library synced by OneDrive or similar holds
dehydrated "files on demand" placeholders, and `ffmpeg -i` on one triggers a full hydration
download. That turns an offline, free, two-minute scan into hours of network transfer, and it
is invisible in WSL2 development. Detect with
`getattr(os.stat(p), "st_file_attributes", 0) & (FILE_ATTRIBUTE_OFFLINE | RECALL_ON_DATA_ACCESS)`
(`0x1000 | 0x400000`; the attribute does not exist off Windows, hence the `getattr` default)
and list them in their own row, never probed.

**The probe needs a timeout (eng review, issue 2).** `extract._default_runner:80` calls
`subprocess.run` with no `timeout`, so a file on an unreachable network share hangs the whole
scan and leaves the child alive after Ctrl-C. Add `timeout` to `_default_runner` and translate
`subprocess.TimeoutExpired` into `ExtractError`; the scan then counts that file as unreadable
and moves on. Fixing it in the shared runner also removes the same hang from the single-file
flow and from any future bulk.

One `ffmpeg -i <file>` per file. Parse from its stderr:

- duration, from the existing `Duration:` line (`extract._parse_duration`, reused);
- **audio bitrate, from the per-stream `Audio: mp3, 44100 Hz, stereo, ..., 128 kb/s` line, NOT
  from the `bitrate:` field on the `Duration:` line.** The latter is the container average and
  on a video file is dominated by the video track.
- Fallback when the `Audio:` line carries no `kb/s` (common on VBR): derive
  `size * 8 / duration` **only when the probe shows no `Video:` stream**. That derivation is
  the container average, which on a video file is dominated by the video track and would read
  as 1500-4000 kbps, tripping the 1b re-encode trigger on everything. For a file that has a
  video stream and no audio `kb/s`, bitrate is `None`.
- `None` bitrate means the file is never re-encoded. Never act on a guess.

**Nothing in increment 1 consumes bitrate or `has_video`.** They are probed and cached here
anyway, deliberately: the probe is the expensive part, and the separate 1b doc would otherwise
have to re-walk and re-spawn ffmpeg over the whole library to get them. Accepted carry-forward,
not scope creep. Their parser is tested here because that is where the parser lives.

Widen `extract._probe_duration` into a public
`probe_media(source: Path, exe: str, runner: Runner) -> MediaProbe`. Keep the existing `exe`
and `runner` parameters: the `runner` seam is what lets the tests inject captured stderr
without spawning ffmpeg, which the test list below depends on.

### Cache

`output/.scan-cache.json`, entries keyed by `(resolved path, size, mtime_ns)`.

- Shape: `{"schema": 1, "entries": {"<resolved-path>|<size>|<mtime_ns>":
  {"duration": float|null, "audio_kbps": float|null, "has_video": bool}}}`. The key is the
  three parts joined by `|`; a path containing `|` is not possible on Windows.
- A missing or different `schema` discards the whole file.
- Corrupt or unreadable JSON: discard and re-probe. Never fail the scan on a cache problem.
- `duration: null` means "probed, and the probe produced no `Duration:` line", i.e. a cached
  negative. A file that was never probed has no entry at all. Cached negatives are not re-probed.
- No eviction. Entries whose key no longer matches are simply not hit; the file is rewritten
  from live results at the end of each scan, so stale entries fall out naturally.
- **Atomic publish (eng review, issue 3).** Write `.scan-cache.json.part`, then `os.replace`,
  exactly as `extract_audio` publishes an mp3 (`extract.py:240`). A direct overwrite would be
  truncatable by the very Ctrl-C the flush exists to survive, and the schema rule would then
  discard the whole file: 500 re-probes at the worst possible moment. Sweep a stale `.part` on
  the next run.
- Single-process only; no locking. The console runs one scan at a time.

### Cancellation

Ctrl-C during a cold scan aborts to the menu and flushes the partial cache first, so the work
already probed is not lost. Consistent with `batch.Cancellation`'s contract, though the scan
needs no process termination: `ffmpeg -i` exits in milliseconds.

### Tables

`ui.table` (`ui.py:444-459`) is a **two-column key/value renderer** taking `Sequence[Choice]`,
not a six-column grid. Increment 1 does NOT add a new UI seam. Each folder is one row: the key
is the folder path relative to the scan root, the value is a packed, column-aligned string:

The rendered form is given once, in the Menu entry section below. If the packed form proves unreadable on real data, a proper multi-column seam is increment 2's
problem, not this one's.

**Transcript detection.** Transcripts are `<date>-<sanitized stem>.txt`, so the stem is not a
filename prefix and a naive `startswith` would make `Лекция 1` match `2026-01-01-Лекция 10.txt`.
**Build an index once, do not compare pairwise (eng review, issue 6).** Reading
`output/transcripts` per source and compiling a pattern per (source, transcript) pair is
`O(files x transcripts)` with a regex build inside the inner loop: 150k compilations on a
500-file library with 300 transcripts, inside a 30-second budget. Instead, list the directory
ONCE and parse each transcript filename back to its stem with a single pre-compiled pattern:

```python
_TRANSCRIPT_NAME = re.compile(r"^\d{4}-\d{2}-\d{2}-(?P<stem>.+?)(?:-\d+)?$")
index: Counter[str] = Counter()
for path in transcripts_dir.glob("*.txt"):
    m = _TRANSCRIPT_NAME.match(path.stem)
    if m:
        index[m["stem"]] += 1
```

Each source is then one dict lookup on
`naming.sanitize_stem(source.stem, fallback="transcript")`. `O(files + transcripts)`, no regex
in the loop. Note `sanitize_stem(stem, *, fallback)` takes a REQUIRED keyword-only `fallback`
(`naming.py:36`).

Note `sanitize_stem(stem, *, fallback)` takes a REQUIRED keyword-only `fallback`
(`naming.py:36`); calling it positionally or without it is a TypeError. The count is still
ambiguous under duplicate stems, which is exactly what the scanner exists to surface, so the
column reads "N candidate transcripts" and the collision report disambiguates.

**Summary detection is NOT in increment 1.** `summarize.save_raw_result:308-311` names the
file from the LLM title, so no back-link from a source file exists. Adding a `source_path`
field to the summary JSON is a prerequisite for that column and is deliberately out of scope
here.

### Rough cost projection

Priced against the tier the operator has selected: `config.load_settings(...).model_tier`
resolved through `ModelConfig.tier(name)`. The figure is labelled with that tier's name,
because switching tiers changes it several-fold.

The chain, closed-form (no synthetic string is materialised, see the note on cost below):

1. `words = seconds * WORDS_PER_MINUTE / 60`
2. `chars = words * CHARS_PER_WORD`
3. `body = guard.estimate_input_tokens("а" * SAMPLE, prompt_overhead=0) / SAMPLE * chars`,
   rounded up. The sample is Cyrillic (`"а"`), which `guard` rates at 0.60 tok/char against
   0.30 for everything else: a Latin sample would halve the headline figure, and CLAUDE.md
   requires the estimate to run high. `prompt_overhead=0` is passed explicitly here; the
   overhead is added back per phase in step 5.
4. `K = max(1, ceil(body / model_config.chunk.phase_target_tokens))`
5. `phase_input_tokens = [ceil(body / K) + PROMPT_OVERHEAD] * K`, then
   `cost.estimate_cost_synthesis(phase_input_tokens, tier,
   per_call_output_tokens=model_config.guard.output_tokens_estimate)`
   *(SUPERSEDED 2026-09-04, TD-24: the signature is now `output_cap=` + `reconcile_floor=`,
   and the output side is per-tier `output_per_input_ratio`, not a flat per-call constant.)*

**Step 5 is where the first draft of this doc was wrong, in the forbidden direction.**
`guard.estimate_input_tokens` folds a flat `_PROMPT_OVERHEAD_TOKENS = 1000` in ONCE, while
`estimate_cost_synthesis`'s contract is that EVERY element of `phase_input_tokens` already
includes the overhead. Splitting one total across K phases therefore under-counts input by
`1000 * (K - 1)`, biasing the estimate LOW against CLAUDE.md's "estimate Cyrillic high". The
overhead must be added per phase, after the split.

`_PROMPT_OVERHEAD_TOKENS` is private to `guard`. Either expose it as a module constant or
mirror it as named config data; do not re-type the literal 1000 in `scan.py`.

**`chunk.plan_phases` is deliberately bypassed.** Its signature is
`plan_phases(text, cfg, *, estimate) -> list[Phase]` and it bins REAL transcript blocks; at
scan time there is no transcript and no blocks, so K is derived arithmetically from
`phase_target_tokens` instead. This duplicates `chunk._bin_count`'s formula on purpose.

**Why closed-form instead of feeding a real synthetic string.** `estimate_input_tokens` runs
a per-character Python generator (`guard.py:73`). A 3-hour lecture at these constants is
~189k chars; 500 of them is ~95M character tests, on the order of ten seconds, a third of the
whole warm budget, for a number that is linear in `chars`. Sampling once and scaling gives the
identical result at O(1) per file.

New constants, both config data, both seeded high for Russian:
`WORDS_PER_MINUTE = 150`, `CHARS_PER_WORD = 7`. The other two values in the chain
(`chunk.phase_target_tokens` at `config.py:168`, `guard.output_tokens_estimate` (removed
2026-09-04, see TD-24) at
`config.py:129`) already exist and carry their own bias policy.

**The chain runs per file and the results are summed.** K is a per-file quantity; summing
durations first and computing one K would be wrong in both directions.

Deliberately deferred: for a file that has exactly one matching transcript on disk, the real
token count is available offline and free via `guard.estimate_input_tokens` on the actual text,
which beats the wpm heuristic. Not in increment 1.

The scan figure is an **upper bound**, labelled as such. It also does not subtract files that
already have a summary on disk (summary detection is out of scope below), so re-scanning an
already-processed folder quotes full price for work that would not be repeated.

### Collision report

Count duplicate `naming.sanitize_stem(source.stem)` values across the whole tree and list every
group with more than one member. This is free at scan time and is the operator-visible evidence
for the naming problem above.

### Menu entry

`_MAIN_MENU` (`menu.py:826-832`) is `tuple[Choice, ...]` and `Choice = tuple[str, str]`
(`ui.py:56`): a value and a ONE-LINE label, rendered by `ui.select`. There is no description
or hint field, and position 3 is already `("transcript", "Saved transcript")`. A multi-line
hint in the menu is therefore not renderable without the new UI seam this increment has
already refused.

So: append one row before Settings, and print the explanation with `ui.info` once the flow is
entered, which is where every other flow already does its talking.

```text
("scan", "Scan a folder"),
```

Hint printed on entry (English, matching the rest of the console):

```
Walks a folder and every folder under it, counts what is there, and prices
the summaries before you spend anything. Reads only. Writes nothing but its
own cache. Tells you which files share a name, which is the one thing that
will silently corrupt a paid run later.
```

Number keys are POSITIONAL (`ui._bind_number_keys`), so appending a row before Settings
re-numbers Settings and Exit for the operator's fingers. That is the documented behaviour of
adding a menu row here and is called out in `_MAIN_MENU`'s own comment.

Table rows render in English too, for one language per increment:

```
Course-1/          12 files   18h 04m   14.2 GB   9 transcript candidates
Course-1/bonus/     3 files    2h 11m    1.8 GB   0 transcript candidates
```

Byte formatting reuses `menu._human_size:524`, which moves to `ui.human_size` (eng review,
issue 5): `menu.py` will import `scan.py` for the flow, so `scan.py` importing `menu.py` back
would be a cycle, and two copies of the formatter would show the same volume differently in
two places. `menu._selection_bytes:536` is NOT reused: it re-`stat`s, while the scan already
holds every size in `MediaFile`.

(CLAUDE.md says console strings are Russian by design; the console as written is English
throughout. This entry follows the code, not the doc. Worth reconciling separately.)

### Where the dollar figure goes

Not a column. After the per-folder table, a second two-column `ui.table` block carries the
totals: selected files, total hours, projected upper-bound cost with the tier name, duplicate
stem groups, unreadable files.

### Tests

CLAUDE.md requires ruff + mypy + tests on every push to `main`. The scanner is almost all pure
functions, so this is cheap:

- the `Audio:` stream bitrate parser, against captured real ffmpeg stderr samples
  (320 / 128 / VBR-without-kb-s / video-with-audio / no-audio-stream)
- unreadable detection (no `Duration:` line, `OSError` on stat)
- cache round-trip, schema mismatch discard, corrupt-JSON discard
- the projection chain against a known duration, asserting the per-phase overhead is present
  K times, not once (the regression test for the bias bug above)
- collision grouping, including stems that differ only after `sanitize_stem`
- walk: `output/` skipped, junction loop terminated, suffix filter honoured
